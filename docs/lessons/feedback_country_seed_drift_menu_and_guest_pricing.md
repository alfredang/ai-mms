---
name: Country DB seed drift can break guest pricing and category menus per-country
description: Each country runs its own database cloned from a seed; the clone can drift from SG's in ways that break only one country's storefront, identically across all its categories
type: feedback
---

When a single country's storefront shows an empty homepage sidebar and/or empty category sliders (CMS `{{block type="ultimo/product_list_featured" ...}}` renders 0 products) while other countries are fine, don't assume it's a code/layout bug or a CDN cache issue — check that country's own database for seed drift first. Each country (SG/MY/GH/NG/BT/IN) runs its **own separate MySQL database** provisioned from `seed/country-base.sql.gz` (see `docs/country-instance-runbook.md`), not one shared catalog DB. The seed can drift after cloning, and the drift is invisible from the code — every template/layout file is identical across countries.

**Why:** On Ghana's `mms_gh` database (2026-06-19 incident), two independent seed-drift bugs combined to look like one mysterious "nothing renders" symptom:

1. **Homepage sidebar empty.** `app/design/frontend/ultimo/default/template/infortis/ultramegamenu/categories.phtml` hardcodes `$categoryId = 3` and calls `renderMe(TRUE, 3, depth)`, which walks `catalog_category_flat_store_<id>` for category 3's children. Those children had `include_in_menu = 0` in GH's DB, while SG's *own, separately-numbered* equivalent categories had `include_in_menu = 1`. `Mage_Catalog_Model_Resource_Category_Flat::_loadNodes()` filters `WHERE include_in_menu = 1` — flip it and the menu silently returns `''` (the template's `if (!$html) return '';` swallows it with no error, no exception, no log entry).
2. **Category sliders (carousel) on CMS homepage content render 0 products.** `Infortis_Ultimo_Block_Product_List_Featured::_getProductCollection()` → `Mage_Catalog_Model_Layer::prepareProductCollection()` builds an `INNER JOIN catalog_product_index_price ... AND customer_group_id = 0`. OpenMage hardcodes anonymous/guest visitors to `customer_group_id = 0` (`Mage_Customer_Model_Group::NOT_LOGGED_IN_ID`, not configurable — see `app/code/core/Mage/Customer/Model/Group.php:39`). GH's `customer_group` table had **no row with id 0 at all** — only `1 (General)` and `2 (NOT LOGGED IN)`, i.e. the "NOT LOGGED IN" label had drifted onto id 2 instead of 0. Because the price indexer iterates existing `customer_group` rows, it could never produce `customer_group_id=0` rows in `catalog_product_index_price` no matter how many times it was reindexed — the missing row, not a stale index, was the actual cause.
3. Also found empty on this DB: `cataloginventory_stock_status` had zero rows for every `website_id` (same failure mode as [[feedback_malaysia_stock_status_empty]] in user memory, but here hitting every website in this DB, not just one).

All three were silent: no PHP exception, no 5xx, `cache-control: no-store` ruled out HTTP caching, and `flush cache` + hard reload did nothing because the *data* was correct-shaped-but-empty, not stale.

**How to apply — diagnostic order when a single country's category/listing pages or nav look broken:**

1. `SELECT customer_group_id, customer_group_code FROM customer_group;` — confirm a row with `customer_group_id = 0` exists. If missing, anonymous-visitor pricing can never be indexed. Fix: `INSERT INTO customer_group (customer_group_id, customer_group_code, tax_class_id) VALUES (0, 'NOT LOGGED IN', <tax_class_id matching group 1>);` — but `customer_group_id` is `AUTO_INCREMENT`, so inserting literal `0` needs `SET sql_mode = CONCAT(@@sql_mode, ',NO_AUTO_VALUE_ON_ZERO');` first, or MySQL silently assigns the next auto-increment id instead.
2. `SELECT website_id, COUNT(*) FROM cataloginventory_stock_status GROUP BY website_id;` and `SELECT website_id, customer_group_id, COUNT(*) FROM catalog_product_index_price GROUP BY website_id, customer_group_id;` — compare row counts across `website_id`/`customer_group_id`, not just "is the table empty."
3. For nav-specific emptiness: `SELECT entity_id, include_in_menu, is_active FROM catalog_category_flat_store_<id> WHERE parent_id = <hardcoded parent>;` — compare against another country's flat table for the *conceptually equivalent* category (entity IDs are **not** shared across country DBs — SG's "Infocomm Technology" and GH's "Computer Programming And Infocomm Courses" are different entity_ids with similar names, not the same row).
4. After any data fix: reindex the specific indexer (`Mage::getSingleton('index/indexer')->getProcessByCode('catalog_product_price')->reindexEverything();` for price — don't hand-write `INSERT`s into `catalog_product_index_price`, it has real tier/rule pricing logic, unlike `stock_status` which is a safe 1:1 copy from `stock_item`), then flush cache.
5. CLI debugging via `php -r` against `Mage::app()` needs two workarounds in this install: pass a real *website* code (e.g. `Mage::app('ghana', 'website')`, not `'default'`), and pre-seed `$_SESSION = array();` before `require Mage.php` or any code path touching `customer/session` (e.g. `Mage_Catalog_Model_Layer::prepareProductCollection()`) throws `Unable to start session.` — this install's session backend (Redis) isn't reachable from a bare CLI script.

See also [[feedback_malaysia_stock_status_empty]] for the original single-symptom version of failure mode #3.
